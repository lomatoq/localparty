# HeyPals: системные правила UI и проверка замечаний

27 сентября 2026. Статус: предложение для просмотра пользователем, не утверждённый редизайн. Production-код этим документом не меняется.

Основание: все 24 пункта `heypals-screen-notes.txt`, предоставленные пользователем экраны и галерея `.localparty-build/screen-review`. Лично просмотрены изображения №103, 242, 286, 363, 393, 423, 433. Остальные строки ниже — требования из замечаний, а не утверждение о самостоятельно подтверждённом дефекте. Старые снимки показывают исходную проблему; закрывать её можно только новым снимком настоящего исправленного экрана. Скриншот не доказывает исправную физику, управление или доступность.

## Общие правила

### R1. Типографика: выразительная консоль с ясной иерархией

Уточнение пользователя: **жирный и наклонный шрифт сам по себе подходит и не является дефектом**. Пользователь хочет действительно другие шрифты и выразительный характер; проблема — одинаковая визуальная сила разных уровней и несогласованность оформления. Пользователь допускает и другие стили: весь интерфейс не обязан быть bold italic. Не делать интерфейс автоматически нейтральным и не превращать upright или italic в обязательное правило. Bold italic допустим для названий, навигации, действий и выбранных игровых показателей, если роли и читаемость различаются.

Три направления в интерактивном макете одного экрана, с одинаковыми данными и геометрией:

- **A — Exo 2, спортивная консоль:** новый геометрический технический характер; настоящий italic700–900 для названий, активного меню, больших действий и отдельных цифр; normal500/600 или italic500/600 для вспомогательных слоёв. Иерархию создают размер, вес, цвет и пространство, а не полный отказ от наклона. [Официальный Google Fonts пакет](https://github.com/google/fonts/tree/main/ofl/exo2), [metadata](https://raw.githubusercontent.com/google/fonts/main/ofl/exo2/METADATA.pb) подтверждают отдельный italic-файл, ось веса100–900, cyrillic и cyrillic-ext. [OFL1.1](https://raw.githubusercontent.com/google/fonts/main/ofl/exo2/OFL.txt). Прямой файл настоящего наклонного начертания: [Exo2-Italic variable TTF](https://raw.githubusercontent.com/google/fonts/main/ofl/exo2/Exo2-Italic%5Bwght%5D.ttf); normal: [Exo2 variable TTF](https://raw.githubusercontent.com/google/fonts/main/ofl/exo2/Exo2%5Bwght%5D.ttf).
- **B — Manrope, геометрический UI:** новый широкий характер normal500/600 для пояснений и имён,700/800 для главного; в текущем прототипе Exo 2 Italic в коротких игровых акцентах. Использовать конкретный [Google Fonts Manrope](https://github.com/google/fonts/tree/main/ofl/manrope) с его [OFL1.1](https://github.com/google/fonts/blob/main/ofl/manrope/OFL.txt). Не выдавать искусственный наклон Manrope за настоящий italic. Не путать пакет с новым Manrope V5 с отдельным соглашением на сайте автора.
- **C — контрольный Rubik:** текущий Rubik с той же новой композицией помогает увидеть эффект иерархии отдельно от новой гарнитуры. Это не предложение оставить старый шрифт вместо запрошенных новых. Системный стек остаётся запасным вариантом на случай ошибки загрузки, а не четвёртым показанным дизайном.

Сохранять лицензию рядом с новым шрифтом. Проверить реальные беларускія І/Ў и русские Ё, а не только латиницу. Не заменять настоящее начертание CSS skew и не растягивать глифы. Имена сохраняют введённый регистр. Не вставлять случайный шрифт в одну панель. Размеры старта для телефона: пояснения16/22, подписи14/18, имена16–18/22, заголовок24/28, счёт28–40/1.1; цифры `tabular-nums`. Это предложения для сравнения, не универсальная норма. На ТВ проверять фактическую высоту глифов и чтение с дивана: XAG101 ориентирует на высоту тела текста26px при1080p (это не равно CSS font-size26px). Тестовая строка: «Пётр · Аляксандра · Ёжик · Ілля · Ўладзімір · 0:59 · 1000».

### R2. Единая геометрия ТВ

Вычислять `safeTop` как фактический нижний край самого низкого элемента постоянной шапки, включая чёлку; `safeBottom` как верх постоянной нижней панели или нижнюю безопасную границу. Центр композиции = `(safeTop + safeBottom) / 2`. В область вписываются не только поле, но имена, карточки, эффекты и границы объектов. Не добавлять одинаковый фиксированный отступ ко всем играм. Рабочее расстояние от шапки16–24px при720p, пропорционально при1080p; декор может заходить под шапку, информация и управление — нет. Не уменьшать поле ради невидимого запаса. Для 3D менять camera framing, для2D viewport transform, не сами координаты физики.

### R3. Результаты и имена

Строка результата: место в фиксированной компактной колонке, имя в гибкой, очки выровнены справа. «1 место» — цельная подпись, а не отдельно разорванные «1 / PLACE». Сетка ориентировочно `52px minmax(0,1fr) max-content`, padding16, gap12, min-height72. Для узкого экрана место бейджем «1», понятие объяснено заголовком таблицы. Не зажимать короткое имя; длинному доступны две строки, резерв не забирать счётом. Полный список всех участников, включая четвёртого и далее; при нехватке высоты скролл списка, действия доступны вне скролла. При равных итоговых показателях показывать одинаковое место. Если правила конкретной игры предусматривают тай-брейк, брать порядок из движка и объяснять критерий, а не пересчитывать победителя в UI. Не подсвечивать случайного единственного «победителя» при настоящей ничьей. Свой игрок отмечен «Вы», не только цветом. Общий компонент поддерживает разные смыслы итога: индивидуальные места, победившая команда, совместная победа/поражение, время и турнирный исход. Не превращать командную или кооперативную игру в выдуманный индивидуальный рейтинг; данные и критерий исхода остаются ответственностью игрового движка.

### R4. Телефон: использовать высоту по смыслу

Шапка, содержимое, нижние действия — отдельные области. Ключевое действие в зоне большого пальца, инструкция рядом с ним. При избытке места распределять между смысловыми группами, не раздувать кнопку на весь экран. При недостатке места контент скроллится без перекрытия паузой/назад. Одно действие Flappy/похожих игр — квадратная большая кнопка с ограничением ширины, например clamp(152px,52vw,208px); не высокий прямоугольник на всю оставшуюся площадь. Минимальная интерактивная область проектно48×48 CSSpx; это выше базового WCAG2.2 AA24×24 с исключениями, не подмена требований. Игровая кнопка имеет видимые idle/pressed/disabled/countdown состояния. Pointer cancel, blur и reconnect снимают удержание.

### R5. Старт/пауза/результат — общие компоненты

Старт: название, одна фраза цели, одна схема управления, свой цвет/команда, состояние готовности. Не одинаковая пустая заглушка. Пауза: фиолетово-розовая полупрозрачная подложка и небольшой blur сцены; ясное «Пауза», кто поставил, кто может продолжить. Зелёный не цвет всего overlay. Gameplay input и simulation остановлены согласованно; после возобновления нет сохранённого joystick/tap. Результат отвечает «кто / какое место / почему / что дальше», не только декоративный подиум.

### R6. Информация без дублирования

Один авторитетный счёт/таймер на одном экране. Для одинокого таймера центрировать цифры вертикально в шапке; при подписи центрировать всю пару. Фраза инструкции полезна до действия, но постоянная техническая подпись под чёлкой не нужна. Имена/счёт на сцене имеют светлый текст и тёмную стабильную подложку; важная команда обозначается и цветом, и именем/маркером.

### R7. Три уровня игровых эффектов

- Уровень1, обычное попадание: короткий локальный flash/bounce120–180ms, маленькая прибавка очков, без тряски камеры.
- Уровень2, важное действие/комбо: локальная вспышка и частицы250–450ms, одна подпись600–900ms. Пример Swarm Gate: красный hit и отскок; смерть — scale вверх+fade+взрыв, без задержки до исчезновения.
- Уровень3, победа/раунд: читаемый баннер и короткое празднование; 700–1200ms motion, итог остаётся доступен до следующего действия. Цветовая вариация по событию, не случайный набор эффектов.

Всплывающий текст не пересекает шапку, имя, прицел и управление; сдвигать якорь внутрь safe area. Несколько попаданий агрегировать, ограничивать одновременно видимые подписи. При reduced motion убирать тряску/масштабирование камеры/длинные траектории, сохранять статичный смысл и счёт. Никакой информации только через цвет. Проверять вспышки, длительность, перенос и наложения отдельно; красный не означает необходимость мигания всего экрана. Время выше — проектные предложения для просмотра, не научно доказанный оптимум.

### R8. Поле и окружение

Декор поддерживает игровую геометрию. Герои, ядра, мишени, линии траектории и ворот важнее бэка. Любые башни/карточки получают отдельные непересекающиеся зоны; менять только рендерный якорь там, где физику менять не требуется. Для Marble Bloom фон заполняет ширину; трасса сохраняет пропорции и видимость целиком, без растяжения шаров. Новые наборы окружения сначала отдельными вариантами на согласование.

## Как принимать, а не объявлять «всё красиво»

1. Полная матрица36 игр×телефон/ТВ×ожидание/игра/пауза/финал, дополнительно роль/выбор/прицел/ход/выбывание там, где состояния существуют. Неприменимое помечено причиной. Отсутствующий снимок = открытая работа, не пройдено.
2. Стабильный номер предыдущего экрана сохранить. Новые случаи получают суффикс/новый номер, старые комментарии не переезжают. У каждого: размер, роль, игроки, состояние, дата, статус и ссылка на правило.
3. Для каждого предложенного исправления показать до/после на одинаковом состоянии и размере, с настоящими игровыми данными. Отдельно отмечать макет и настоящий runtime.
4. Автоматические проверки: нет overflow/пересечений обязательных HUD областей, видимы все строки результатов, загружены шрифты, нет missing translation, pointer release работает, поведение паузы корректно. Геометрические проверки не заменяют просмотр.
5. Ручной визуальный проход:320×568,375×667,393×852, phone landscape;ТВ1280×720,1920×1080. Короткие/длинные кириллические имена, ничья,0 и большие очки. Не выдавать список автотестов за доказательство качества композиции.
6. Пользователь принимает примеры A/B/C и отдельные игровые стили. Общую систему распространять после выбора; локальные однозначные дефекты не требуют редизайна всего проекта.

## Первичные рекомендации, проверенные27.09.2026

Это актуально доступные официальные источники, а не выдуманный отдельный «стандарт2026».

- [Apple HIG — Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games/): адаптация интерфейса игры к платформам и людям. [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) — официальный раздел; его страница требует JavaScript, полный текст инструментом не получен, поэтому точные нормы из неё здесь не приписываются.
- [Xbox XAG101 — Text display](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101): проверять фактическую высоту текста, расстояние просмотра и масштабирование; ориентир консоли26px body-height при1080p.
- [Xbox XAG102 — Contrast](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102): HUD оценивается относительно меняющегося фона, нужны устойчивые способы повышения контраста.
- [Xbox XAG117 — Visual distractions and motion](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/117): учитывать отвлекающее движение, настройки эффектов и доступность.
- [WCAG2.2](https://www.w3.org/TR/WCAG22/): обычный текст4.5:1, крупный3:1; информация не только цветом; видимый focus. [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html):24×24 CSSpx с оговорёнными исключениями. Наш48px — собственная более щедрая цель для игрового телефона.
