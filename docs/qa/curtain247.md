## First GL and synchronous work findings

The sports Stage constructor synchronously creates the renderer, static scene, pools and performs resize before marking warmup pending and calling `renderer.compileAsync(scene,camera)`. Texture and model helpers start asynchronous loads. The warmup promise catches compile failure and still marks ready in its finally callback.

The sports loop skips its main renderer entirely while authoritative phase is waiting. Initial GL draw calls do occur while building the environment, however: they are auxiliary Three.js scene/PMREM work, not a main Stage.scene render. CompileAsync ready followed by two outer-shell RAFs and100ms does not prove the actual scene/shadow pass or initial scene texture uploads occurred before opening. Later-created materials remain outside the initial scene's compile coverage.

The247 test page instruments compileShader/linkProgram and first draw calls, pending/ready changes and available long-task observations with the outer curtain state. An optional route-injected renderer wrapper additionally compares `scene === Stage.scene`, separating main renders from auxiliary environment renders. Wrapper durations measure CPU API calls, not GPU elapsed time. Instrumentation exists only in test pages. Native WKWebView/receiver threading and shared device GPU contention still require root's full-app/physical instrumentation.

Corrected baseline Chrome+WebKit Curling/Bowling launch-waiting traces all compile under revealing/closed cover. Their first auxiliary GL draw occurs before warmup: Chrome Curling341.7ms/Bowling303.1ms; WebKit Curling294ms/Bowling233ms, measured within the iframe navigation. This alone is insufficient evidence of prepared main content.

The additional real WebKit Curling start trace reproduces the specific readiness gap: waiting/preparation has34 auxiliary renders and zero main scene renders; first actual main render happens after force-start with curtain idle, warmup ready, phase playing and Stage.clock0.04. Its CPU call takes355ms. The matched isolated candidate drains5 initial requests, compiles49ms and performs one320ms main render behind revealing cover with phase waiting and clock0. Its WebGL2 fence completes after2 asynchronous polls/19ms. The first playing main render subsequently takes37ms. This single sample demonstrates moving first-use work under cover, not a physical-cast FPS improvement or general9.6x application speedup.

The same actual start adds34 linked programs/68 shader calls after idle in baseline versus3 programs/6 shader calls after idle in the isolated candidate. Dynamic gameplay-created materials still require work, and the37ms call is still above a60fps frame budget. Initial preparation therefore reduces a concrete startup spike without claiming that every subsequent shader/effect is prepared or no jank remains.

## Production integration and missing-state race

The production helper is `games/sports_siege/public/scene-readiness.js`. Initialization waits initial loader requests, compiles the current scene, makes one direct real main-scene render without a match/object/effect update or Stage clock advance, then waits an asynchronous WebGL2 fence before the existing ready publication. The neutral module uses options with a10s default deadline and no private QA deadline global. Default runtime retains only minimal Stage preparation status; event arrays and the window proof require explicit `data-scene-readiness-qa`. The normal playing cadence, camera, geometry and effect quality are retained.

The deadline bounds asynchronous asset/compile/fence waits; it cannot preempt a synchronous JavaScript renderer call. Missing textures drain loader accounting, stalled responses/fences reject into the original host catch/finally readiness publication, context loss exits, and a no-fence context explicitly records unverified GPU completion when diagnostics are enabled. Temporary loader wrappers/timers/fences are restored/deleted on completion/failure; synchronous staticScene/pools/resize errors restore hooks and rethrow the original error.

Actual production routing revealed an integration defect which the earlier route-overridden candidate could not expose: the Sports worker explicitly allowlists JS modules, so the new module returned404. The first failed `curtain-unknown-baseline/` report is an HTTP integration diagnostic, not evidence for the state guard. `games/sports_siege/server.js` now allowlists `/scene-readiness.js`. The harness records failed JS HTTP responses and requires explicit shaderWarmup `ready` for the four Stage games, so missing readiness no longer passes. This was repaired before the passing real-production runs.

Separately, while holding actual first authoritative waiting-state snapshots, the unguarded loop advances with `this.state` absent. The repaired-route baseline held43 snapshots and advanced Stage.clock to1.66s with84 effect updates and45 recorded normal main draws. The isolated single-condition guard `!this.state` held the same kind of real snapshots with clock0/object and effect updates0/normal unknown-state renders0, then released the latest actual waiting snapshot, started real playing and returned to the exact menu. Only after this reproduction and isolated proof was that single guard promoted. The production guard repeats the proof with41 held snapshots and all unknown-state counts0. This is independent from the one deliberate clock0 readiness render and does not block matching simulation after actual state arrives.
