# Локальная оптимизация: до и после

База — свежий `main` (`8bbad77`), а не прежняя ветка до слияния. Каждый прогон выполнен отдельно: production launcher + embedded worker, настоящий Chromium ТВ, активные протокольные пульты, до 30 секунд. Один запуск на вариант, случайные игровые состояния могут отличаться. Это сравнение на Mac M1 Max / Node 22 / loopback, не гарантия производительности iPhone/Wi-Fi/AirPlay.

CPU: 100% = одно ядро; RAM — p95 RSS сервера. Поток — исходящие игровые данные всем пультам и ТВ без сетевых заголовков. RTT p95 — WebSocket ping/pong, не «палец → пиксель». Частота — полные состояния ТВ; у DrawGuess новые штрихи идут отдельными сообщениями.

## Проверка вариативности Jenga

Повтор тем же сценарием, 16 игроков и 30 секунд: CPU 18.4 → 14.6%, поток 6.066 → 4.385 MB/s; RTT p95 7.86 → 5.67 ms.

Снижение CPU и трафика повторилось. RTT p95 у базы заметно различается между запусками, поэтому улучшение задержки Jenga не заявляется. Измеритель посылает ping каждые 500 ms, а физический callback работает каждые 50 ms; взаимная фаза этих таймеров может влиять на долю ping, попавших внутрь расчёта. Это возможное объяснение вариативности, а не измеренная причинность. Два повтора недостаточны для уверенного вывода о хвостах задержки.

Во всех семи измерениях «после» нет зарегистрированных ошибок страницы ТВ/соединений. Это отдельные старты игр; ошибки последовательного переключения экранов и ограничения общих проверок описаны в [отчёте реализации](implementation.md).
