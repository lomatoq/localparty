# Motion, rendering and performance inventory — 26 games

Source audit, 2026-09-12. No gameplay source changed by this audit. This is an implementation map, not a claim of measured frame rates or physical-phone validation. Read game-creator skill, creator profile, studio operating system and technical architecture references. Root owns the immediate Arcade mechanics changes; do not overwrite them.

## Findings that matter first

1. **Arcade presentation samples raw 30 Hz snapshots at requestAnimationFrame frequency.** `games/arcade/public/app.js` draws player, ball and bag positions directly from `state`. At 60/120 Hz it repeats positions, producing visible stepping even with good server physics. Add a separate display-state map with time-based smoothing (`1-exp(-rate*dt)`), reset on mode/round/respawn and large teleport, preserve server state for collision and scoring. Angle interpolation must take shortest arc. Do not smooth decisive death/hit events or add input latency to phone feedback.
2. **Arcade sends full shared state to every phone 30 times/second.** `games/arcade/server.js` uses one `game.view()` then JSON.stringify per recipient. Snake already sends incremental trail to hosts and no trails to phones: preserve this. Hungry food and Flappy pipes do not need to be sent to controllers. A controller projection can retain phase/mode/title/time/timer/players scores/alive/dead/hits/connected, punchTurn and bag.last; strip world arrays. Serialize the shared host packet once. Measure bytes before claiming improvement.
3. **Kart interpolation depends on monitor refresh rate.** `games/kart/static/host.js:drawCars` uses `.28` every frame. Convert to `1-exp(-19.7*dt)` to retain roughly the 60 Hz feel at 120/144 Hz. `drawTrack()` redraws the entire static road, start checker and text each frame; cache a background canvas and invalidate on size/theme/track changes.
4. **Crane repeatedly runs DOM ranking layout every snapshot.** `games/crane/public/client.js:renderPlayers` reads offsets, appends all rows and starts FLIP animations while server broadcasts at 20 Hz. Cache ranking/content keys. Only perform ordering FLIP on changed order and update score text on change. Cache static city/star background. Keep authoritative Rapier simulation unchanged.
5. **Snake's full retained trail is restroked every animation frame.** Network deltas already exist; use a persistent trail canvas keyed by round, append only new segments, draw heads/names separately. Clear on reset/reconnect/full snapshot. Bounded particles cannot be appended to this permanent canvas.
6. **Atlas recoloring must be cached.** Never extract/tint pixels per entity per frame. Cache by asset id + player color + atlas version. Use separate neutral base/color mask (source-in for mask), then untouched highlights/details. Preserve grayscale shadows in mask if using multiply. Outline, contact shadow, name and team cue remain procedural and legible.
7. **Canvas presentation and domain simulation must stay separate.** Existing party game renderers use snapshot positions and procedural primitives; augment draw functions, not server collision radii. Generated art's transparent padding is not a collider. Do not delay a match waiting for remote art: local preload, fallback primitive, reveal when ready.

## Integration order and shared rendering contract

Recommended implementation: small local `PartyArt` utility + manifest, not a new engine. API `draw(ctx,id,x,y,width,height,{rotation,tint,pivot})` returns false until local image ready so callers retain primitive fallback. Atlas manifests must supply integer x/y/w/h, normalized pivot, trim bounds, role(base/mask/detail), logical group and default draw size. Use padded cells and no baked text/glow; procedural effects are cheaper and more consistent. Keep art files local and versioned. Use one request/decode per atlas; cache tinted layers by the16 player palette entries only, bounded cache. Separate environments from object atlases to avoid scaling giant textures for tiny props.

Implement first Arcade6 + Party5 + tank/kart/duel shared sprites. Then UI-only family accents, preserving authored drawings and physical3D Jenga. Do not “standardize” every game into one scene. Canvas context save/restore around every sprite avoids leaking alpha/composite/shadow state into names.

## Validation required after atlas integration

- Manifest validator: all rectangles inside image, no overlaps (unless explicitly layered), alpha gutters, pivots finite, required asset ids referenced by26game map.
- Two players and16players, host1920x1080 and3440wide; controllers320x640 and402x874. Capture waiting, playing, feedback/reveal, final for every distinct engine and mode-specific scene.
- Compare visible art bounds against original collider/debug overlay; tank turret, knife forward axis, bag rope pivot and opposing cowboy flip are specific checks.
- Offline/missing atlas fallback must still show controls/game and start without delay. No stale lobby card when phase changes.
- Fixed input sequences at30/60/120renderHz: same server outcomes, interpolated motion time independent. Reset interpolation at round/respawn/teleport.
- Count frame durations over representative16player run; report median/p95, no fabricated60fps claim. Measure WebSocket bytes host vs phones for Hungry/Snake before/after projection. Verify pause does not advance physics/effects tied to gameplay time.
- Accessibility: reduced-motion disables decorative loops/large shake, never removes hit/result feedback. Mobile pointer controls must retain touch-action and no text selection; do not place decorative sprites over input targets.

Unresolved hardware gate: actual iPhone motion sensor, permission flow and perceived Punch impulse need physical Safari validation; source/browser automation cannot prove physical sensor behavior.
